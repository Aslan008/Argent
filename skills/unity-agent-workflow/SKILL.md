# Работа с Unity как агент: файлы → dotnet → batchmode

Агент не видит окно Unity и не кликает в нём. Зато у него есть три надёжных канала:

| Канал | Что даёт | Цена | Когда |
|---|---|---|---|
| **Файлы** (чтение/правка, grep, YAML) | Код, шейдеры, UXML, сцены/префабы/материалы как текст, GUID-ссылки | мгновенно | всегда — основа |
| **`scripts/fast_check.py`** (dotnet build по .csproj Unity) | Ошибки компиляции C# | 5–30 с | после каждой правки C# |
| **`scripts/unity_batch.py`** (Unity -batchmode) | Настоящая компиляция всех сборок, импорт шейдеров/ассетов, запуск своего кода в редакторе: тесты, бенчмарки, снимки, правка ассетов через API | 20 с – 3 мин; проект должен быть закрыт | перед сдачей работы; для тестов и замеров |

Если в среде есть MCP-мост к открытому редактору (например, `com.unity.pipeline`, Unity MCP) —
им удобно делать `recompile` + чтение консоли без закрытия Unity. Этот скилл описывает путь,
который работает **везде**, где есть терминал и Python/dotnet: Claude Code, Codex, Cursor,
Copilot-агент, Gemini CLI и т. д.

Скрипты лежат рядом: `scripts/` (запускать из любого места внутри проекта — корень находится сам).
Шаблоны C# — в `assets/` (расширение `.txt`, чтобы Unity их не компилировал, пока они лежат здесь).

Справочники (читать по необходимости):
- `references/cases.md` — **«Что если…»**: разбор типовых ситуаций и ошибок с решениями.
- `references/howto.md` — **«Как узнать / посмотреть…»**: рецепты для всего, что обычно смотрят глазами в редакторе.
- `references/unity-files.md` — форматы файлов Unity и правила их безопасной правки (.meta, YAML, Shader Graph, UXML).
- `references/case-study.md` — реальная сессия: что запускалось, когда, зачем и что из этого вышло.

## 0. Перед началом: разведка (1–3 минуты, экономит часы)

1. **Инструкции проекта**: `AGENTS.md`, `CLAUDE.md`, `README` — конвенции (язык комментариев,
   «не коммитить без просьбы», запреты). Они важнее этого скилла.
2. **Версия и пайплайн**: `ProjectSettings/ProjectVersion.txt` (версия Unity → путь к Unity.exe),
   `Packages/manifest.json` (URP/HDRP, Input System, сетевые пакеты, локальные пакеты `file:`).
3. **Сборки**: где `*.asmdef` (`glob **/*.asmdef`). Код в asmdef **не видит** Assembly-CSharp —
   это ключ к ошибкам «тип не найден» и к тому, куда класть мосты между системами.
4. **Unity открыт?** `Temp/UnityLockfile` занят → batchmode запускать нельзя (см. cases.md).
   `unity_batch.py` проверяет это сам.
5. **git status** — чтобы отличать свои изменения от чужих и не «чинить» чужое.

## 1. Цикл работы

```
понять задачу → найти код (grep/glob) → прочитать целиком нужные места
   → правка (Edit; большие серии — patcher.py) → fast_check.py → (повторить)
   → unity_batch.py (финальная компиляция всех сборок + шейдеры)
   → [если есть логика/рантайм] свой тест через -executeMethod
   → [если важны вид/скорость] бенчмарк/снимок с --graphics
   → уборка временного → честный отчёт
```

### 1.1. Правка файлов
- Читай место правки **целиком** (класс/метод/шейдерный проход), а не кусок вокруг номера строки:
  в Unity-коде много неявных связей (сериализация полей, `[SerializeField]`, имена свойств шейдера,
  `FindPropertyRelative("имя")` в редакторах).
- **Новое сериализуемое поле** — задавай инициализатор (`public float x = 1f;`): в уже сохранённых
  сценах поля нет, Unity создаёт объект (инициализаторы срабатывают) и перезаписывает только
  сохранённые поля — старые объекты получат значение инициализатора. Исключения: элементы списков,
  добавленные в инспекторе «+», копируют предыдущий элемент; `struct` в массивах при ресайзе — `default`.
  Если поведение старых сцен должно остаться прежним — дефолт должен означать «как раньше».
- **Переименование сериализуемого поля** теряет данные в сценах → `[FormerlySerializedAs("старое")]`.
- **Не создавай `.meta` сам** — Unity создаст при импорте (GUID случайный и уникальный).
  Удаляешь ассет — удаляй и его `.meta`. Переносишь — переноси вместе с `.meta` (иначе рвутся ссылки).
- Серия однотипных правок в больших файлах → `scripts/patcher.py` (точное совпадение, проверка
  числа вхождений, сохранение BOM/CRLF). Скрипт правки — во временную папку, не в проект.
- Комментарии/UI — на языке проекта. Стиль — как в окружающем коде.

### 1.2. Быстрая проверка C# — `fast_check.py`
```bash
python <skill>/scripts/fast_check.py                       # сборки с изменёнными по git .cs
python <skill>/scripts/fast_check.py --path Assets/X/Y.cs  # конкретный файл/папка
python <skill>/scripts/fast_check.py --csproj GameCore     # конкретная сборка
python <skill>/scripts/fast_check.py --all                 # всё
```
Как работает и почему так: Unity генерирует `.csproj` для IDE в корне проекта, но обновляет их
**только при синхронизации с IDE** — новые файлы в них отсутствуют, удалённые числятся, и «голый»
`dotnet build` даёт ложные ошибки. Скрипт копирует `.csproj` во временную папку, заново раскладывает
все `.cs` по сборкам (asmdef → своя; `Editor/` → `Assembly-CSharp-Editor`; остальное →
`Assembly-CSharp`) и собирает. Проект не трогается.

Не ловит: шейдеры, UXML/USS, ошибки сериализации/импорта, кодоген (FishNet, Burst, IL-weaving),
`.asmref`, `versionDefines`. Поэтому `fast_check` — для частых итераций, а **финальное слово — за Unity**.

Если `.csproj` в корне нет совсем — `unity_batch.py --method UnityEditor.SyncVS.SyncSolution`
(или попросить пользователя один раз открыть проект в IDE).

### 1.3. Настоящая проверка — `unity_batch.py`
```bash
python <skill>/scripts/unity_batch.py                      # импорт + компиляция всех сборок
python <skill>/scripts/unity_batch.py --wait 900           # дождаться, пока проект освободят
```
Печатает только суть лога: `COMPILE` (error CS), `SHADER`, `EXCEPTION`, `ABORT`, `LICENSE`, `LOCK`,
код выхода и путь к полному логу. Полный лог при сомнениях читай сам (`grep -n "error\|Exception"`).

- По умолчанию `-nographics`: быстро, но **без GPU**. Compute-шейдеры («Kernel not found»),
  рендер, `Graphics.*`, снимки — не работают. Для них `--graphics`.
- Ошибки шейдеров надёжнее видно с `--graphics` (компиляция вариантов под реальный GPU).
- Первый запуск после правок долгий (импорт + компиляция), следующие — 20–60 с.
- Лог Unity шумный: сетевые/лицензионные/Package Manager-сообщения — не ваши ошибки
  (скрипт их фильтрует; см. cases.md «шум в логе»).

### 1.4. Свой код в редакторе — тесты и проверки логики
Шаблон: `assets/AgentProbe_TEMP.cs.txt`. Скопировать в любую папку `Editor/` как `*_TEMP.cs`,
вписать проверки, запустить, **удалить вместе с `.meta`**.
```bash
cp <skill>/assets/AgentProbe_TEMP.cs.txt Assets/<...>/Editor/MyFeatureProbe_TEMP.cs   # и переименовать класс
python <skill>/scripts/unity_batch.py --method MyFeatureProbe_TEMP.Run --grep AGENT_PROBE
```
Принципы, которые делают такие тесты полезными:
- **Сцена в памяти** (`EditorSceneManager.NewScene`) — настоящие сцены пользователя не трогать и не сохранять.
- Каждая проверка печатает `OK/FAIL <что проверено и фактические значения>` с маркером — `--grep`
  вытащит их из лога. Фактические значения в строке экономят повторный запуск при FAIL.
- Подписка на `Application.logMessageReceived` — ловит ошибки, которые код пишет в консоль, а не бросает.
- `EditorApplication.Exit(код)` — результат виден по коду выхода.
- Компоненты с тяжёлым `OnEnable` (GPU, сеть, синглтоны) создавай на **выключенном** GameObject,
  если проверяешь логику; иначе — `--graphics`.
- Undo в batchmode работает, но группы разделяй `Undo.IncrementCurrentGroup()`, иначе
  `PerformUndo` откатит «не то» и тест ложно упадёт.
- В batchmode **нет игрового цикла**: `Update()` сам не зовётся, `Time.deltaTime` не идёт,
  корутины не крутятся. Нужное вызывай вручную (рефлексией для приватных методов).
- Play Mode-сценарии (физика, корутины, сеть) — через Unity Test Framework
  (`-runTests -testPlatform PlayMode -testResults out.xml`), см. howto.md.

### 1.5. Скорость и картинка — бенчмарк и снимки
Шаблон: `assets/AgentBench_TEMP.cs.txt` (замер кадра: прогрев, 3 серии, медиана, ожидание GPU через
`ReadPixels`; снимок в .jpg). Запуск с `--graphics --no-quit`. Снимки смотри как изображения.
- Сравнивай **до/после на одной машине и одной сцене**, «без фичи» — как базу: важна разница, а не абсолют.
- Шум batchmode ±5–10 %: решения на разнице < 0.3 мс не принимай, повтори замер.
- Снимок «до» делай ДО правок — потом его не получить.

### 1.6. Сдача работы
- Удалить всё временное: `*_TEMP.cs` + `.meta`, тестовые текстуры/ассеты, созданные папки
  (только свои! чужие файлы в `Generated/` и т. п. — не трогать). Проверить `git status`.
- После удаления временных скриптов — ещё один `unity_batch.py` (или хотя бы `fast_check`),
  если удалённое могло на что-то ссылаться.
- Отчёт пользователю: что сделано, **как проверено** (dotnet / batchmode / тест / замер / не проверено
  руками в окне), цифры, что не сделано и почему, какие файлы вне зоны задачи изменены,
  что не закоммичено. Если тест падал и почему — тоже сказать.
- Не коммитить без просьбы. Сцены (`.unity`) правь только когда это и есть задача.

## 2. Решения, которые агент принимает сам, и где спросить

Сам: способ проверки, временные тесты, порядок шагов, добавление полей с безопасными дефолтами.
Спросить (или следовать AGENTS.md): правка общих ассетов пайплайна (URP Asset, Quality, Player
Settings), удаление/перенос чужих ассетов, правка сцен вручную, перезапекание тяжёлых данных
(лайтмапы, навмеш, ассеты >100 МБ), смена версий пакетов, всё необратимое.

## 3. Короткие правила, у которых есть причина

- **Один Unity на проект.** Второй экземпляр на тот же проект портит `Library/` или не стартует.
- **Library/ не править и не удалять** без нужды — это кэш на десятки минут переимпорта.
  Удалять `Library/ScriptAssemblies` или `Bee/` — только как крайняя мера (cases.md).
- **Не открывать сцену и не сохранять её из теста** — `EditorSceneManager.SaveScene` в тесте
  перезапишет работу пользователя. Нужна сцена — `OpenScene` без сохранения, правки в памяти.
- **Большие файлы**: сцены по 5 МБ и bake-ассеты >100 МБ не читать целиком — grep/скрипт.
- **Не верить старым выводам.** Код мог измениться: перед утверждением «функция X есть» — grep.
- **Честность в отчёте важнее красивого отчёта**: «проверено тестом в batchmode, руками в окне не
  проверял» — нормальная и полезная фраза.
