### 1. `cargo test` в `crates/argent-tui` падает на `test_bridge_e2e` вне PATH базового Python
- **Дата:** 2026-10-26
- **Симптом:** `process didn't exit successfully ... (exit code: 0xc0000135, STATUS_DLL_NOT_FOUND)`. С добавленным в PATH `%LOCALAPPDATA%\Programs\Python\Python311` тест проходит.
- **Причина:** тест-бинарь линкуется с libpython, а venv-путь `python3.dll` не содержит.
- **Решение:** либо в `tests/test_bridge_e2e.rs` пропускать тест с внятным сообщением, если DLL не найдена, либо добавить в `crates/argent-tui/build.rs`/README строку про PATH. Пока записано как известное ограничение окружения.
- **Разбор (2026-10-27):** пропуск внутри теста не поможет — падение происходит **при загрузке тест-бинаря**, до любого тест-кода: бинарь линкуется с `libpython`, а в venv нет `python3.dll`. `skip_or_fail` в тесте уже есть и работает для случая «мост не запускается»; это шаг раньше.
- **Сделано:** в README, в разделе Native TUI, добавлен абзац «`cargo test` needs the base Python on PATH» с воспроизведением ошибки (`0xc0000135`), объяснением причины и готовыми командами для PowerShell (`$env:PATH`, `$env:VIRTUAL_ENV`, `cargo test`). Отдельно сказано, что тесты сами пропускаются с причиной, когда недоступен мост, — чтобы не путать два разных случая.
- **Статус:** сделано.

### 6b. `test_an_unanswered_select_cancels_instead_of_hanging` вешал весь прогон
- **Дата:** 2026-11-03
- **Где:** `tests/test_answer_timeout.py:43`, `src/bridge/session.py` (`ask_select`).
- **Симптом:** полный `pytest tests` обрывался без итоговой строки. Тест выставлял `ARGENT_ANSWER_TIMEOUT=1`, а `ask_select` читает `ARGENT_QUESTION_TIMEOUT` (по умолчанию 3600 с) — тест часно ждал ответа, которого не будет.
- **Почему это валит весь набор:** `pytest.ini` задаёт `timeout = 300` и `timeout_method = thread`; потоковый метод по истечении убивает процесс, а не один тест. Один зависший тест отменяет весь прогон — остальные результаты теряются.
- **Решение:** тест выставляет ту переменную, которую действительно читает код (`ARGENT_QUESTION_TIMEOUT=1`). Поведение `ask_select` намеренно не менялось: долгое ожидание выбора — это решение «человек думает», а не забытый таймаут.
- **Проверка:** `pytest tests/test_answer_timeout.py -q` — 3 passed за 2.6 с.
- **Статус:** сделано (2026-11-03)

### 7. Колесо крутило поле ввода и панель задач, когда указатель был над чатом
- **Дата:** 2026-10-26
- **Симптом:** прокрутка чата не работала: вместо диалога начинал крутиться текст в поле ввода (казался «историей запросов»), хотя курсор был не над ним. То же ломало прокрутку панели задач.
- **Причина:** `App::wheel` выбирал цель по последней известной позиции мыши, а она обновлялась только событием `Moved`. У события колеса есть своя координата — её никто не читал. - **Решение:** координата берётся из самого события колеса (`ScrollUp/ScrollDown` → `set_mouse_pos`); колесо над чатом сбрасывает подглядку в поле, чтобы оно снова шло за кареткой.
- **Тесты:** `crates/argent-tui/tests/test_bg_window.rs::the_wheel_over_the_chat_returns_the_prompt_to_its_caret`, `the_wheel_scrolls_the_window_not_the_chat`, весь `test_scroll*`/`test_bg_panel`.

### 3a. Роутер: вежливый префикс меняет выбор инструмента
- **Дата:** 2026-10-27
- **Симптом:** `test_routing_invariance_under_polite_prefixes[please ]` — фраза «please открой файл package.json» маршрутизируется в `run_command`, а не в `read_file`. Остальные шесть вежливых префиксов этой же проверки проходят.
- **Где:** `src/leeth/dispatcher.py:466` (арбитр shadow), попадает через `tests/test_leeth_property_based.py:38`.
- **Почему важно:** это не окружение — реальное расхождение в выборе инструмента. Вежливое слово не должно менять действие: в автономном режиме такая подмена означает «прочитать файл» → «выполнить команду».
- **Как воспроизвести:** `.venv\Scripts\python.exe -m pytest "tests/test_leeth_property_based.py::test_routing_invariance_under_polite_prefixes" -q`.
- **Предлагаемое решение:** проверить, не попадает ли «please» в ключевые слова командного маршрута (или не сбивает ли нормализацию), и добавить в набор примеров пары «вежливый префикс + русский глагол чтения».
- **Разбор:** легаси-классификатор (mmBERT здесь недоступен) на английском вступлении переключается в «командную» категорию: `please открой файл package.json` → `run_command(command="package.json")`, то есть просьба **прочитать** файл превращалась в попытку его **выполнить**. Русские варианты проходили только за счёт обучающих данных — нормализатора вежливых вступлений в коде не было вообще.
- **Решение:** `src/leeth/dispatcher.py` — `_strip_courtesy()` снимает ведущие вежливые/разговорные вступления (ru + en: please, could you, would you, can you, kindly, пожалуйста, будь добр, срочно, быстро, попробуй). Снимаются **только для классификатора**: проверка параметра по-прежнему идёт по исходному тексту, и извлечённый фрагмент обязан оставаться его подстрокой, иначе fast-dispatch отклоняется. Если после снятия остаётся меньше трёх символов — возвращается исходный текст.
- **Проверка:** проба до/после — `please открой файл package.json` даёт `read_file(file_path="package.json")`, conf 0.97 (было `run_command(command="package.json")`, 0.96); `tests/test_leeth_property_based.py` — 16 passed; срез `leeth|dispatcher|routing` — 620 passed, 54 skipped.
- **Статус:** сделано.

### 4. Флейк: `test_rust_bridge_deep_lmtrust` — блокировка хода

### 4b. Список разрешённых программ desktop стал мёртвым кодом
- **Дата:** 2026-10-26
- **Где:** `desktop_guard.allowed_apps()`, `argent/config.py: get/set_desktop_allowed_apps`, ключ `desktop_allowed_apps`.
- **Симптом:** после снятия гейта список ни на что не влияет, но остался в конфиге, в `check_window(allowed=...)` и в тестах.
- **Решение (когда руки дойдут):** удалить ключ и функцию `allowed_apps()`; параметр `allowed` в `check_window` оставить (им пользуются тесты).
- **Разбор (2026-10-27):** удалять было бы неправильно — это не косметика. Пока ключ читается конфигом, человек, вписавший список, уверен, что агент может трогать только эти программы; на деле `allowed_apps()` никто не вызывал, а `check_window` везде звался без `allowed`, то есть ограничение не действовало. Список **обещал защиту и не давал её**.

### 4c. Vibe больше не ограничен по времени — остаётся риск «занятого тупика»
- **Дата:** 2026-10-26
- **Ситуация:** стоп теперь только по отсутствию прогресса (3 хода подряд без единого вызова инструмента). Если агент бесконечно *вызывает* инструменты, ничего не добиваясь (пишет один и тот же файл), это не ловится.
- **Отдельный случай:** цепочка `wait_heartbeat` → пробуждение → снова `wait_heartbeat` формально считается «вызовом инструмента», но прогрессом не является. Её ограничивает `AUTO_MAX_WAKES = 40` в `_deliver_wakes` (счётчик сбрасывается реальным вводом).
- **Решение (две части):**
  1. **Счётчик одинаковых вызовов** независимо от результата (`REPEAT_ARGS_WARN = 3`, `REPEAT_ARGS_STOP = 5`), `src/agent/loop_guard.py`. Лестница та же, что у основного правила: для «умных» моделей warn → nudge → stop на 6-м вызове, для остальных warn на 3-м и stop на 5-м. Ожидание не считается работой: `read_background_command`, `list_background_commands`, `subagents`, `wait_heartbeat` исключены. Счётчик сбрасывается сменой инструмента/аргументов и на каждом ходе.
  2. **Главная причина тупика оказалась не в охране, а в автоходе.** `_maybe_auto_continue` (`src/bridge/repl_bridge.py`) считал прогрессом любой ход, где были вызовы инструментов, — а крутящийся ход их как раз и делает. То есть охрана останавливала ход, и через секунду стартовал следующий, бесконечно. Теперь агент запоминает причину конца хода (`_turn_end_reason`), сессия отдаёт её как `last_turn_end` (`src/bridge/session.py`), а автоход после принудительной остановки (`loop guard`, `tool call written as text`) выключает vibe и сообщает об этом вместо нового шага.
- **Тесты:** `tests/test_loop_guard_repeat_args.py` (9) — одинаковый вызов с разным ответом доходит до stop, смена аргументов/инструмента сбрасывает серию, ожидание не считается, обычная работа не задевается; `tests/test_vibe_forced_stop.py` (4) — принудительная остановка прекращает прогон, обычный ход по-прежнему продолжается, правило «3 холостых хода» работает; старое поведение — `test_browser_loop_prevention` и `test_moe_and_platform_cleanup` без изменений (48 вместе); срез `vibe|heartbeat|session|wake|loop_guard|turn_lock` — 459 зелёных, 4 падения только stagehand (нет node-моста, были до правки).

### 4q. Ход заканчивался, когда вызов инструмента уходил текстом
- **Дата:** 2026-10-27
- **Симптом:** модель пишет в ответ `<create_artifact><parameter name="filename">…</parameter></create_artifact>` вместо настоящего вызова. Argent печатает это как обычный текст и завершает ход: работа не сделана, а со стороны выглядит, будто агент «закончил».
- **Причина.** `parse_raw_tool_call` (`src/agent/parser.py`) понимал `write_file`-блок, JSON и битый JSON, но не XML-подобные теги. Дальше в `argent/agent.py:2729` любой непустой текст считался финальным ответом (`break`), поэтому такой «вызов» закрывал ход.
- **Решение:**
  - `parse_xml_tool_call` — читает `<tool><parameter name=…>…</parameter></tool>` и `<tool a="1"/>` обратно в настоящий вызов; тег учитывается только если имя совпадает с реальным инструментом (обычная разметка вроде `<div>` не ловится). Подключён в `parse_raw_tool_call` до JSON-разбора.
  - `looks_like_tool_call_text` + ветка в конце хода: если текст похож на вызов, ход НЕ завершается. Модель получает точное объяснение («вызов записан текстом, он НЕ выполнен, вызови по-настоящему»), до `MAX_TEXTUAL_CALL_CONTINUES = 2` раз, затем остановка с честным сообщением. Счётчик сбрасывается на каждом ходе.
- **Тесты:** `tests/test_textual_tool_calls.py` (9) — читаемый тег реально исполняется, нечитаемый не принимается за ответ, число попыток ограничено; `parse_xml_tool_call` не путает прозу и HTML с вызовом.
- **Статус:** сделано (Python; подхватится при следующем запуске).

### 4u. Весь интерфейс зависал во время работы агента — настоящая причина
- **Дата:** 2026-10-27
- **Симптом:** во время длинного хода приложение переставало отвечать целиком: не набирался текст, не прокручивался диалог, ничего. Не панель и не отдельный виджет — весь интерфейс.
- **Причина 1 (главная).** Поток отрисовки сам заходил в Python: раз в 2 с вызывал `get_state` и, кроме того, сразу после каждого `done`/`error`. `Python::with_gil` ждёт GIL, а GIL держит рабочий поток агента, пока тот думает, стримит и разбирает вывод. Пока агент работал, поток отрисовки стоял — вместе с чтением клавиш и колесом. Отсюда полный паралич, а не «подтормаживание».
- **Причина 2 (усиливающая).** `get_state` → `session.state` → `list_checkpoints`, а это `git for-each-ref` плюс `git merge-base --is-ancestor` на каждую запись: **замерено ~340 мс на реальном репозитории**, на каждый опрос. То есть даже без GIL треть времени уходила на git.
- **Решение:**
  1. Опрос состояния вынесен на отдельный поток: он берёт GIL сам, раз в секунду, и присылает результат событием `ArgentEvent::State`. Поток отрисовки больше не вызывает Python для состояния вообще.
  2. `list_checkpoints` кэшируется (TTL 10 с, ключ — рабочий каталог, чтобы два репозитория в одном процессе не делили ответ), кэш сбрасывается при создании чекпоинта и при подрезке старых. Замер после правки: `session.state` 0–1 мс вместо ~340.
  3. Событие состояния не сбрасывает `overscroll` и не трогает прокрутку — иначе обновление раз в секунду сдёргивало бы читателя вниз.
- **Тесты:** `tests/test_checkpoint_cache.py` (5) — второй вызов не запускает git, новый чекпоинт виден сразу, чужой репозиторий не отдаёт свой список, вызывающий не может испортить кэш, меньший лимит читается из большего; `tests/test_checkpoints.py` — 32 passed; `cargo test` — все наборы ok.
- **Что осталось возможным:** `start_turn` тоже берёт GIL, поэтому отправка сообщения во время тяжёлого хода может подождать. Ввод и прокрутка при этом работают — это следующий шаг, если понадобится.
- **Статус:** сделано; расширение пересобрано и установлено.

### 4v. Картинки в чате и во вложениях — пиксельная мозаика
- **Дата:** 2026-11-04
- **Симптом:** превью картинки в чате и сама картинка при раскрытии настолько пиксельные, что не видно, что на скриншоте; то же у превью прикреплённой к ответу картинки.
- **Причина 1 (свёрнутая карточка).** `cards.rs::image_card_rows` для свёрнутой карточки брал `thumb` — сетку шириной **26 знакомест** (`image_preview.THUMB_COLS`). Для скриншота 1920×1080 это 26×14 пикселей; на всю ширину карточки она не растягивалась (`image_lines_scaled` не увеличивает больше ширины сетки), поэтому картинка была не только мозаичной, но и крошечной.
- **Причина 2 (полоса вложений).** В `ui.rs::attachment_strip` был предел `MAX_COLS = 56` при `MAX_ROWS = 8`: 16:9 при 56 знакоместах — это 16 строк клеток, то есть рисовалась только верхняя половина кадра. Предел ширины мешал, а предел высоты молча обрезал.
- **Причина 3 (classic-тема).** В `view.rs` (тема Classic) картинка под карточкой не рисовалась вообще — превью жило только в ветке Premium (`cards::item_view`). Пользователь на classic-теме видел только имя инструмента.
- **Что не лечится размером сетки:** полублок `▀` даёт 1 пиксель по ширине и 2 по высоте на знакоместо. На 200-колоночном окне вся картинка — 200×112 пикселей, то есть 1/10 скриншота 1920×1080; текст на нём не читается ни при какой сетке.
- **Решение:**
  - Карточка в чате рисуется из широкой сетки `full` (96 знакомест) и при свёрнутом виде (не шире 56 знакомест — `FOLDED_PREVIEW_COLS`), и при раскрытом (на всю ширину карточки). 26-колоночная миниатюра больше не используется для рисования.
  - При раскрытии карточки фронтенд **по требованию** просит сетку экранного размера (`preview_full(path)`, 320 знакомест = 320×180 пикселей) и подменяет кадр в кэше карточек (новый `seq` сбрасывает кэш строк). В опросе состояния по-прежнему едет дешёвая сетка 96 знакомест (~20 КБ), поэтому «не нагружать зря» соблюдено: тяжёлая строится один раз по клику (замер: 12 мс, 225 КБ base64).
  - `preview_full` принимает путь: клик по старой карточке открывает её картинку, а не последнюю опубликованную.
  - Полоса вложений: предел теперь на **строки** (10), а не на колонки — ширина считается из пропорций (16:9 → ~35 знакомест), кадр виден целиком, без обрезки верхней половины.
  - Полноэкранный просмотр: в подписи появился `O — открыть в системе`, клавиша `O` отдаёт **оригинальный файл** системному просмотрщику (`ReplBridge.open_image` → `os.startfile`), `Esc` закрывает как раньше. Для картинки из буфера, у которой файла не было, `vision._open_path` пишет временный файл из уже закодированных байт. `queue_image` теперь несёт `path` (view_image, browser_screenshot, desktop_*, буфер, Telegram), чтобы открывался оригинал в полном разрешении, а не уменьшенная до 1568 px копия, ушедшая модели.
  - Classic-тема рисует ту же картинку под карточкой (`view.rs`), чтобы поведение не зависело от темы.
- **Замеры (1920×1080):** было — карточка 26×14 px, раскрытая 96×54 px, полоса 56 колонок с обрезом; стало — карточка 56×31 px, раскрытая до ширины карточки из сетки 320×180 px, полоса 35×20 px без обреза, полный экран 320×180 (на 200-колоночном окне — 200×112).
- **Тесты:** Rust — `the_card_preview_is_drawn_from_the_wide_frame_not_the_thumb`, `a_wider_card_draws_a_wider_picture`, `the_strip_shows_the_whole_frame_instead_of_its_top_half`, расширенный `a_click_on_the_thumbnail_opens_the_whole_screen` (в нём же проверяется путь к оригиналу); `cargo test` (test.bat) — все наборы ok. Python — `tests/test_pending_images.py` (+2: путь существует и это оригинал), `tests/test_image_preview_payload.py`, `tests/test_vision_deep.py` — 26 passed.

- **Причина 1.** `App::absorb_streamed_output` удалял живой вывод только при точном совпадении с результатом (`squash(live) == squash(result)`). `run_command` возвращает текст, обёрнутый в `Exit code: N` + `OUTPUT:\n…`, а живой поток — это только stdout процесса, поэтому равенства не было никогда, и дубль оставался всегда.
- **Причина 2.** Перед живым выводом в том же месте лежит строка авто-одобрения: `console.print` из `approval.py` идёт через trap и становится таким же `MessageItem::Output`. Сравнивать «весь блок» нельзя даже вхождением.
- **Причина 3.** Живые строки хранят ANSI-коды (`\x1b[2m …`), а результат приходит из Python уже очищенным — сырые байты не совпадают.
- **Решение:** блок снимается с конца построчно: каждый `Output`-ряд, чей текст (без ANSI, по словам) содержится в результате, — дубль карточки и удаляется; первый ряд, которого в результате нет (строка одобрения, обрезанный хвост), становится границей и остаётся. Свёрнутая карточка и так показывает «N строк · первая строка», так что первые строки живут в блоке.
- **Второе:** в `argent/approval.py` все строки авто-решения переведены с `[dim]` на `[yellow]` (одобрено) и `[red]` (отклонено): dim на тёмной теме уводит цвет в фон, а это единственный след того, что команда прошла без человека.
- **Тесты:** `crates/argent-tui/tests/test_output_dedup.rs` (7: точное совпадение, обёртка `Exit code/OUTPUT`, живой хвост, которого нет в результате, цвет в живой строке, строка одобрения перед выводом, чужой инструмент); `tests/test_approval_visibility.py` (2 — ни одна строка авто-решения не печатается тусклой); полный `cargo test` (test.bat) — EXIT=0; `pytest` по гейту (approval/vibe/automation_modes) — 207 passed.
- **Статус:** сделано; расширение пересобрано (`maturin build --release`, 13:17) и установлено (pyd 13:18). Новое поведение включится после перезапуска окон Argent.
