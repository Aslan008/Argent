# План развития Argent (2026-10-11)

Источник: сверка `claude_architecture_findings.md` с кодом Argent + три вопроса владельца:
(1) что брать на прицел, (2) визуальное восстановление чата, (3) управление ПК.
Отдельное жёсткое требование владельца: **режим Ultracode обязан работать и с локальными моделями, не вешая ПК**,
даже когда основная локальная модель занимает все ресурсы.

Статус (2026-10-12): **M0–M7 реализованы и покрыты тестами** (см. «Итоги реализации» ниже). Порядок по решению владельца от 2026-10-13: M7 → M6 → M5; зависимости `pywinpty` и `uiautomation` разрешены и установлены в `.venv`. В git ничего не коммитится без просьбы владельца.

---

## 0. Правила работы над планом

- Корневые решения, не заплатки (память `no-bandaids-principle`).
- Тесты и maturin только через `.venv`; тесты герметичные (HOME, пустой конфиг на тест, cwd) — память `tests-hermetic-rules`.
- Правки файлов с CRLF — через скрипт, который сохраняет перевод строк и компилирует перед записью (память `sandbox-editing-quirks`).
- Rust-часть (`crates/argent-tui`) после правок: `cargo test` + пересборка через maturin; golden-векторы `tests/test_stream_golden.rs` обновлять вместе с Python-стороной.
- Коммитить и пушить только по просьбе владельца. README (EN и RU разделы) обновлять вместе с каждой пользовательской функцией.
- Загрузка внешних файлов и зависимостей (например `pywinpty`, `uiautomation`) — только с разрешения.
- Обучение и тяжёлые прогоны — только на Kaggle (не относится к этому плану, но правило остаётся).
- Личные данные из `.argent/input_history` никуда не копировать.

### Решения владельца (2026-10-11)

1. Порядок этапов: M0 → M1 → M2 → M3 → M4 (M5–M7 позже).
2. Приоритет процесса и потоки — **для всех локальных провайдеров** (Ollama, KoboldCPP, llama-server и т.д.); LM Studio в Argent пока нет — архитектуру делаем расширяемой (адаптеры серверов), провайдер добавляется отдельно.
3. Облачный советник в Ultracode — **обязателен**; модель советника настраивается вручную, как облачная, так и локальная (по образцу `critic_model`/`critic_provider`).
4. Зависимости — можно, если они дают чистый плюс (проверять каждую отдельно).
5. Управление ПК — шире (M5).
6. Память — на обоих уровнях, но не обязательно: проектный и/или глобальный каталог, как у Claude: используется то, что существует.

Что НЕ сделано в этих этапах (честно; всё остальное из первой версии этого списка добито в разделе
«Добивка», ниже):
- Вытеснение рабочего запроса срабатывает при ближайшем фрагменте ответа: пока модель обрабатывает промпт и ничего не
  отдаёт, ждать приходится до первого фрагмента (клиент не может прервать сервер на лету).
- Использование микромоделей Leeth для проверок в воркфлоу — сознательно не подключено: в конвейере нет вызова
  большой модели, который микромодель решала бы надёжнее разбора, уже сделанного кодом (вердикт критика, статус
  процесса, коды возврата проверок); лишний источник ошибок без выигрыша по полосе.
- Живая проверка на настоящих Ollama/KoboldCPP и на облачном советнике не выполнялась (нет эталонной конфигурации;
  сервер Ollama на ПК владельца не запущен, а его запуск — это нагрузка, ради которой всё и затевалось);
  вся логика проверена тестами со стендами (в том числе сквозной прогон через настоящие процессы под-агентов и git worktree).

### 3.1 Живая цензура секретов (`SecretRedactor`)

## 5. M3 — Resource Governor: как не повесить ПК локальными моделями

### 5.1 Идея
«Рой» агентов в Ultracode — логическое понятие, а не N физических копий модели. Локальный сервер (Ollama,
llama-server, KoboldCPP) один и обычно держит одну модель; N одновременных запросов не дают N-кратного ускорения,
они делят одни и те же ядра/видеопамять и растягивают задержку для всех, включая основной диалог.
Поэтому для локальных моделей нужна **не «ограниченная параллельность», а планировщик с одной узкой полосой
и приоритетами**: все обращения к модели — основной агент, под-агенты, критик, сжатие, ночная память — проходят
через общие «полосы» (lanes), а нагрузка на ПК контролируется отдельным монитором.

### 5.2 Классы бэкендов
| Класс | Примеры | Ёмкость полосы по умолчанию |
|---|---|---|
| `cloud` | OpenRouter, Claude, DeepSeek, … | по лимитам провайдера (из заголовков/ошибок 429), по умолчанию 4 |
| `local_shared` | Ollama / llama-server на этом ПК | **1** (больше только если сервер явно настроен на `num_parallel` и есть запас RAM/VRAM) |
| `local_exclusive` | модель грузится внутри процесса (`llama_cpp`) | 1 процесс на весь Argent; под-агентам запрещено грузить вторую копию |

Класс определяется по провайдеру и `base_url` (localhost/127.0.0.1/::1/192.168.*), с ручным переопределением.

### 5.3 Компоненты
1. **LaneScheduler** (`src/agent/lanes.py`).
   - Билеты в `.argent/run/lanes/<lane>/` : файл `<priority>-<timestamp>-<pid>.ticket` с heartbeat; владеет полосой
     тот, чей билет первый по `(priority, time)`. Работает между процессами (под-агенты — отдельные процессы).
     Мёртвые билеты снимаются по `psutil.pid_exists` и возрасту heartbeat.
   - Приоритеты: **P0** интерактивный ход основного агента; **P1** критик/советник, ответ на вопрос пользователя
     из под-агента; **P2** рабочие под-агенты Ultracode; **P3** фон (сжатие, предгенерация, память, ночные задачи).
   - **Кооперативное вытеснение.** Нельзя оборвать генерацию на сервере «на лету», но можно оборвать поток на
     клиенте: при появлении P0-билета рабочий запрос P2/P3 отменяется (закрытие стрима), шаг повторяется позже.
     Ограничение: шаг не повторяют больше N раз, потом он ждёт «окна» (простой модели).
   - Короткие шаги: у воркеров лимит `max_tokens` и небольшой контекст, чтобы отмена стоила недорого.
2. **PressureMonitor** (`src/agent/pressure.py`, переиспользует `SystemResourceAuditor` из
   [local_inference.py](../local_inference.py)).
   - Раз в секунду: загрузка CPU, свободная RAM, VRAM (через `nvidia-smi`, редко — 2 с таймаут), температура/троттлинг
     (если доступно), **задержка UI** (проверка пульса цикла TUI: если кадр опаздывает > 300 мс — перегрузка).
   - Гистерезис: пауза новых билетов при CPU > 85% дольше 5 с, RAM < 1,5 ГБ, VRAM свободно < 1 ГБ, лаг UI;
     возобновление при заметно меньших значениях. Аварийно: лаг UI > 1 с → отмена текущих P2/P3-потоков.
   - Учитывает чужую нагрузку (сборки, тесты, игры): это не наши процессы, но для пользователя это тоже «завис».
3. **ProcessNiceness.** Под-агенты и фоновые воркеры стартуют с пониженным приоритетом
   (`BELOW_NORMAL_PRIORITY_CLASS` через `psutil`/creationflags; на Windows — также EcoQoS, если доступно).
   Сервер модели (Ollama) — другой процесс: менять его приоритет только по явной настройке `lower_model_server_priority`.
4. **Ограничение потоков/контекста** (опционально, настройкой): для Ollama `num_thread = физические ядра − 2`,
   ограничение `num_ctx`; для llama-server — параметры запуска показываются как рекомендация, а не меняются молча.
5. **Калибровка** при первом включении Ultracode на локальной модели: короткий замер (время до первого токена,
   токенов/с, свободные ресурсы) → профиль `.argent/run/calibration.json`, привязан к модели и «отпечатку» железа.
   По нему считаются оценка времени и лестница деградации (5.5).
6. **Единая точка входа.** Все провайдеры вызываются через `lanes.acquire(lane, priority)` как контекстный менеджер
   (и стрим, и обычный вызов). Тут же — учёт ожидания, чтобы показывать пользователю «ждёт очереди 12 с».
7. **Группировка по моделям.** Роли Ultracode по умолчанию используют **ту же** модель (разный системный промпт),
   чтобы Ollama не выгружал/загружал веса. Если нужны разные модели, шаги группируются по модели.

### 5.4 Гарантии для пользователя («что обещаем»)
- Один физический «рой» не запускается: на локальной модели параллельность = 1, остальные агенты ждут в очереди.
- Основной диалог всегда впереди очереди; рабочие шаги выполняются в «окнах» (пока вы читаете ответ, пока идут
  сборка/тесты, пока вы печатаете) и сдают место по первому требованию.
- Если ПК нагружен чем-то ещё, очередь сама встаёт на паузу и показывает почему.
- Кнопка/команда `/ultracode pause|stop` и `Esc` действуют мгновенно (отмена потоков, остановка процессов дерева —
  уже есть `_kill_process_tree`).

### 5.5 Лестница деградации (выбирается автоматически по калибровке, можно закрепить вручную)
| Уровень | Что делает | Когда |
|---|---|---|
| 3 Полный рой | Planner + параллельные воркеры + Critic + Advisor | cloud-модель или сильное железо с большим `num_parallel` |
| 2 Конвейер | Planner → воркеры **по одному** → Critic, чекпоинты между шагами | типичная локальная модель, ПК с запасом |
| 1 Облегчённый | план + todo + один проход критика, без под-агентов | слабое железо, малая модель, мало RAM |
| 0 Обычный агент | как сейчас | калибровка показала, что режим не даст пользы (малая модель плохо планирует) |

### 5.6 Приёмка M3
- 4 одновременных под-агента на локальной модели не увеличивают отклик ввода в TUI (p95 < 150 мс при замере
  таймера в тесте с имитацией сервера).
- Билеты корректно переживают убитый процесс (тест с принудительным завершением).
- Нет «голодания»: P2 получает полосу, когда P0 нет; P0 никогда не ждёт P2/P3 дольше одного шага.
- В `local_exclusive` попытка загрузить вторую копию модели блокируется с понятным сообщением.

### 5.7 Тесты
Фальшивый провайдер с управляемой задержкой и отменой; подмена `psutil` для сценариев давления; многопроцессные
тесты на заглушках (по образцу `argv_builder` в `SubagentManager`); свойства порядка билетов; длительный soak-тест
вручную на реальной Ollama.

### 5.8 Риски
- Отмена потока не освобождает сервер мгновенно (зависит от бэкенда) — учитывать «остывание» перед следующим билетом.
- Файловые билеты на сетевых дисках/OneDrive — держать каталог в `%LOCALAPPDATA%`, а не в проекте, если путь синхронизируется.
- Сложность: если справедливость файловых билетов не устроит, запасной вариант — локальный шлюз (маленький
  OpenAI-совместимый прокси на 127.0.0.1, который принимает все запросы и сам держит очередь). Не берём сразу:
  лишняя подвижная часть и проксирование стрима.

## 6. M4 — Ultracode / Workflow

### 6.1 Что это в Argent
Режим оркестрации, а не «больше токенов на размышление»:
Planner разбивает задачу на подзадачи с зависимостями и проверками → Executor-воркеры (под-агенты, при правках — в git
worktree) → Critic на каждый значимый шаг → Integrator применяет патчи по порядку и гоняет тесты → итоговая проверка.
Состояние сохраняется на диск, ход можно прервать, продолжить и посмотреть.

### 6.2 Компоненты
- `src/agent/workflow/` : `plan.py` (граф шагов, схема, валидация), `engine.py` (исполнение, повторы, бюджеты),
  `roles.py` (промпты Planner/Executor/Critic/Integrator; Critic переиспользует [critic.py](../src/agent/critic.py)),
  `store.py` (`.argent/workflows/<id>.json`, возобновление), `report.py` (итог для пользователя).
- Включение: `/ultracode on|off|status|pause|stop`, ключевое слово `ultracode` в запросе
  (настройка `workflow_keyword_trigger`), только в рамках сессии, как у Claude.
  Ручная смена `reasoning_effort` пользователем выключает режим.
- Усилия: Planner и Critic — максимум доступного (`xhigh` у облачных; для локальных — ограничение по бюджету
  токенов, чтобы не уйти в бесконечное «размышление»).
- Безопасность наследуется: `ChildGate`, `FORBIDDEN_TOOLS`, `plan_mode`, deny/ask-правила, чекпоинты
  ([checkpoints.py](../src/agent/checkpoints.py)); патч воркера применяется только после проверки Critic и тестов.
- Бюджеты: токены, время, число шагов, число попыток на шаг; превышение → остановка с отчётом, а не тихое продолжение.
- Прозрачность: перед запуском показать план, уровень (3/2/1), оценку времени и стоимости; в TUI — панель
  шагов с состоянием, очередью полосы, давлением на ПК; зеркало в Telegram.

### 6.3 Особенности локальных моделей
- Уровень выбирается из калибровки (5.5); по умолчанию на локальной модели — «Конвейер» с параллельностью 1.
- Планировщик на малой модели ненадёжен → строгая схема плана (constrained decoding уже есть в
  [constrained.py](../src/agent/constrained.py)), валидатор, максимум глубины и числа шагов; при неверном плане —
  откат на уровень ниже, а не бесконечные перепланирования.
- Контекст воркера — «пакет контекста» (задача + нужные файлы + критерии), а не вся история.
- Для маршрутизации и дешёвых проверок использовать уже имеющиеся CPU-микромодели Leeth (классификация,
  быстрые проверки формата), чтобы не тратить полосу большой модели на тривиальное.
- Ночной режим: длинный воркфлоу ставится на ночь через `src/automation` (прогон без нагрузки в рабочее время).
- Облачный «советник» для локального ПК — **только по явному согласию** и с предупреждением, что данные уходят наружу.

### 6.4 Приёмка
- На локальной модели режим не включает больше одного физического потока генерации; ввод в TUI остаётся отзывчивым.
- Падение процесса на середине → `/ultracode resume` продолжает с последнего завершённого шага.
- На эталонной задаче (рефакторинг 3 модулей с тестами) режим даёт не худший результат, чем обычный агент, и честно
  показывает затраты.

### 6.5 Риски
Малые модели плохо декомпозируют (поэтому лестница деградации); накопление ошибок по цепочке шагов (поэтому проверки
и патчи, а не прямые правки); пользователь ожидает «быстрее» — а локально режим медленнее (поэтому оценка времени и
ночной режим).

## 7. M5 — Управление ПК и приложениями

Сейчас: список окон, скриншоты, буфер обмена ([desktop.py](../src/automation/desktop.py)), открытие программ через
оболочку, клики и ввод только в веб-страницах (`browser_action`). Нативного ввода мыши/клавиатуры нет.

- **Инструменты.** `desktop_find_element` (дерево UI Automation по окну: имя, роль, состояние, прямоугольник),
  `desktop_click` (по элементу UIA, запасной вариант — по координатам), `desktop_type`, `desktop_hotkey`,
  `desktop_focus_window`, `desktop_wait_for` (появление окна/элемента). Предпочитать UIA (устойчиво к разрешению и
  темам), пиксели — только запасной путь.
- **Цикл «наблюдай → действуй → проверь».** После каждого действия возвращать новый список/скриншот элементов; без
  свежего наблюдения слепые серии кликов запрещены.
- **Безопасность.** Все новые инструменты в `MUTATING_TOOLS` режима плана и в `FORBIDDEN_TOOLS` под-агентов; каждое
  действие через гейт одобрения с описанием («нажать "Удалить" в окне X»); белый список приложений, в которых
  разрешено действовать (по умолчанию пустой); запрет ввода в окна с полями пароля, UAC, системные диалоги, менеджеры
  паролей; глобальная горячая клавиша аварийной остановки; ограничение скорости и числа действий в серии;
  аудит-журнал действий.
- **Окружение.** Работает только на «активном рабочем столе» пользователя (контекст `_attached_user_desktop`
  уже есть); при заблокированном экране — отказ.
- **Малые модели.** Vision не обязателен: UIA-дерево — текст. Для моделей без vision так даже надёжнее.
- **Зависимости.** `uiautomation` или `pywinauto` — только с разрешения владельца; `SendInput` через `ctypes` без
  зависимостей — базовый вариант.
- **Тесты.** Против тестового Win32-окна (маленькое приложение-«мишень» в тестах); юнит-тесты гейта и запретов;
  ручной чек-лист (Блокнот, Калькулятор, Проводник).

## 8. M6 — PTY для интерактивных команд

- Сейчас команды идут через `subprocess` с закрытым stdin, зависание на запросе обнаруживается по тишине и шаблонам
  ([command_ops.py:215](../tools/command_ops.py)).
- Дизайн: опциональный режим `pty=true` для `run_command`/фоновых команд на ConPTY (`pywinpty`), поток через FSM из 3.3,
  возможность ответить на запрос (`send_background_command` уже есть), ограничение по времени и тишине сохраняется.
  Фолбэк на нынешний путь, если ConPTY недоступен.
- Зависимость `pywinpty` — по разрешению. Секретные подсказки (`password:`) по-прежнему не заполняются автоматически.
- Тесты: `git` с запросом, `npm init`, `python -i`, `ssh` с запросом ключа (в песочнице), обрезка вывода.

## 9. M7 — Markdown-память и ночная консолидация

- Сейчас: один `.argent/memory.json` для малых моделей ([memory_manager.py](../memory_manager.py)).
- Дизайн: каталог `.argent/memory/`: `MEMORY.md` (индекс ≤ 200 строк) + узлы `<slug>.md` с YAML-шапкой,
  разделами «Контекст / Why / How to apply», ссылками `[[узел]]`. Инструменты `memory_read`, `memory_write`,
  `memory_search`; в системный промпт попадает только индекс (дёшево).
- Совместимость: существующий `memory.json` остаётся источником «рабочей памяти» хода; миграция — одноразовая, по
  команде.
- Консолидация («dream»): расписание через `src/automation`, запуск только когда ПК простаивает и подключён к питанию,
  приоритет P3 в полосе (M3); этапы: просмотр логов сессий → создание/слияние узлов → разрешение противоречий →
  обрезка индекса. Результат — отчёт и откат (файлы под git/чекпоинтом), без тихих удалений.
- Приватность: память не содержит сырых секретов (используется `SecretRedactor`), не уходит в облако без согласия.

## 10. Что сознательно НЕ берём

- Скользящие окна лимитов 5 ч / 7 дней: это механика подписки Claude; у Argent провайдеры с разными правилами.
  Достаточно уже существующего учёта токенов/стоимости и лимитов самих провайдеров.
- Пункты про скрытую телеметрию и подмену моделей — это описание поведения чужого продукта; из них берём только
  принцип прозрачности: никаких молчаливых подмен модели и отправки метаданных наружу (в Argent этого нет, оставить
  как правило проекта и добавить тест на отсутствие сетевых вызовов телеметрии).

## 11. Сквозные вопросы

- **Документация.** Раздел в README (EN + RU) по каждой функции; страница «Ultracode и локальные модели».
- **Конфигурация.** Новые настройки в `config.py` с геттерами/сеттерами в существующем стиле; команды в
  `src/cli/commands`; подсказки в `/doctor` (доктор показывает класс бэкенда, ёмкость полосы, калибровку).
- **Совместимость.** Старые сессии, старые конфиги, слабые модели (короткие профили инструментов).
- **Наблюдаемость.** Метрики полос (ожидание, занятость), события давления, причина паузы — в лог и в `/status`.
- **Откат.** Каждая функция за флагом; выключение возвращает прежнее поведение.
